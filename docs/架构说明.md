## 2. 技术选型与理由

| 层 | 选型 | 版本基线 | 理由 |
|---|---|---|---|
| 编排 | LangGraph | 1.2.6 | 需要显式状态图（图片分支、命中判断、兜底、工单抽取），且自带 checkpointer 做多轮记忆 |
| Web | FastAPI + uvicorn | 0.141 / 0.52 | 原生支持 multipart 图片上传、SSE 流式、静态托管，一个进程搞定前后端 |
| 存储 | SQLite + FTS5 + sqlite-vec | Python 内置 / 0.1.9 | 单文件零部署；向量与业务数据同库同事务，无需引入 Chroma/FAISS |
| 嵌入 | 本地 BGE-M3（1024 维） | 本机已存在 | 中文检索效果好、完全离线、无 API 成本；默认 CPU 推理以省显存 |
| 对话 | Ollama `qwen3:4b`（默认）+ DeepSeek API（备用） | — | 默认离线私有；备用通道保证演示不中断 |
| 视觉 | OpenAI 兼容多模态网关 | — | 需要看懂报错截图与实物照片 |
| 前端 | 原生 HTML/CSS/JS | — | 零构建、启动即用、样式精确可控 |
| 测试 | pytest（+ 现有 Node 文档校验） | — | 核心逻辑离线可测，模型调用打桩 |

## 4. 数据模型

```sql
-- 知识库
documents(id INTEGER PK, filename TEXT, sha256 TEXT UNIQUE, mime TEXT,
          page_count INT, chunk_count INT, status TEXT, uploaded_at TEXT)
chunks(id INTEGER PK, doc_id INT REFERENCES documents(id) ON DELETE CASCADE,
       ordinal INT, section TEXT, page INT, text TEXT, char_len INT)
chunks_fts   -- FTS5(chunks.text)，external content 指向 chunks
vec_chunks   -- sqlite-vec: vec0(chunk_id INT PK, embedding FLOAT[1024])

-- 会话
conversations(id TEXT PK, session_id TEXT, title TEXT, status TEXT,
              ticket_draft_json TEXT, created_at TEXT, updated_at TEXT)
messages(id INTEGER PK, conv_id TEXT REFERENCES conversations(id) ON DELETE CASCADE,
         role TEXT, text TEXT, image_path TEXT, vision_json TEXT,
         citations_json TEXT, trace_json TEXT, created_at TEXT)

-- 工单
tickets(id INTEGER PK, ticket_no TEXT UNIQUE, conv_id TEXT,
        customer_request TEXT, product_model TEXT, fault_phenomenon TEXT,
        error_info TEXT, tried_actions TEXT, urgency TEXT, suggestion TEXT,
        citations_json TEXT, status TEXT, source TEXT,
        created_at TEXT, updated_at TEXT)
ticket_events(id INTEGER PK, ticket_id INT, from_status TEXT, to_status TEXT,
              note TEXT, created_at TEXT)

-- 多轮记忆（LangGraph SqliteSaver 自建表，由 langgraph-checkpoint-sqlite 管理）
```

约定：状态流转只允许 `待处理 → 处理中 → 已解决 → 已关闭`（允许回退到「处理中」），每次流转写一条 `ticket_events`。

## 5. 检索设计

1. **解析**：PDF 逐页取文本（保留页码）；MD 按标题层级切分并记录章节路径。
2. **分块**：目标 300–500 字，优先在段落/标题边界断开，块间保留 1 句重叠；每块记录 `doc_id / section / page / ordinal`。
3. **嵌入**：BGE-M3 输出 1024 维向量，L2 归一化后写入 `vec_chunks`；模型不可用时置「仅关键词」模式。
4. **召回**：两路并行——
   - 关键词路：FTS5/BM25，查询串做中文切分与转义；
   - 向量路：sqlite-vec KNN 取 Top-N。
5. **融合**：RRF（Reciprocal Rank Fusion）合并两路排名，得到统一打分。
6. **阈值**：融合分低于阈值 → 判定未命中，走兜底话术（对应 F5 验收）。
7. **返回**：Top-K（默认 4）片段，附文档名、页码、分数，供生成与页面展示。

## 5.1 打分公式与阈值标定

三路信号归一后加权求和（缺哪个通道该项为 0）：

```
score = 0.45 · 覆盖率 + 0.35 · 向量相似度 + 0.20 · RRF 排名分
```

- **覆盖率** = 问题 token 在片段里出现的比例（中文二元切分后统计）；
- **向量相似度** = 归一化向量的余弦，再按 `[0.35, 0.85]` 线性拉伸 —— BGE-M3 对不相关
  文本也会给出 0.35~0.45 的相似度，不设地板会把无关片段抬得过高；
- **RRF** = `1/(60+rank)` 两路求和后按通道数归一。

**标定实测**（真实 BGE-M3 + 2 份中文资料，2026-10-12）：

| 问题 | 最高分 | 判定 |
|---|---|---|
| 硒鼓怎么更换 | 0.670 | 命中 ✅ |
| 打印机显示 E05 是什么意思 | 0.500 | 命中 ✅ |
| 保修期是多久 | 0.627 | 命中 ✅ |
| 无线网络连不上怎么办 | 0.648 | 命中 ✅ |
| 预订国际航班机票价格 | 0.247 | 未命中 → 兜底 ✅ |
| 今天北京天气怎么样 | 0.208 | 未命中 → 兜底 ✅ |

命中类 0.50~0.67 与未命中类 0.21~0.25 之间有明显间隔，因此阈值默认取 **0.35**。
若换成别的嵌入模型或语料风格差异大，用 `scripts/calibrate.py` 重跑一遍再调
`RETRIEVE_MIN_SCORE`。

## 6. LangGraph 图设计

**State 关键字段**：`messages`、`current_text`、`image_path`、`vision_result`、`query`、`retrieved`、`hit`、`answer`、`citations`、`ticket_draft`、`mode`（`ollama`/`fallback`/`keyword_only`）。

```
START → prepare ──有图片──→ vision_understand ─→ rewrite_query
             └──无图片──────────────────────────→ rewrite_query
rewrite_query → hybrid_retrieve → judge_hit ──命中──→ generate_answer → update_draft → END
                                            └─未命中─→ fallback_answer ─→ update_draft → END
```

- **记忆**：`thread_id = conversation_id`，checkpointer 持久化到 SQLite，刷新页面/重启服务后上下文仍在（F1）。
- **每轮重置**：`prepare` 节点会清空本轮的图片描述、检索结果、回答与引用，只有工单草稿跨轮保留——
  否则上一轮上传的图片信息会串进这一轮的检索（有专门的回归测试守着）。
- **兜底确定性**：未命中知识库时**不调用模型**，直接输出模板话术（`FALLBACK_USE_MODEL=false`）。
  兜底本身就是"不许编"的场景，交给模型润色反而可能把「内部资料未收录」改写成模糊说法，
  实测还出现过编造无关建议的情况；确定性输出同时保证模型全挂时这条路依然可用。
- **工单草稿**：`update_draft` 每轮增量合并已抽取字段，右侧栏实时展示（F7）。
- **结束会话**：`POST /api/conversations/{id}/close` 触发 `tickets/extractor.py` 定稿，写入 `tickets` 并返回工单号。

### 6.1 工单抽取的可靠性设计

定稿时字段来自两路，**模型结果为主体、规则草稿补空缺**（`merge_draft(模型字段, 规则草稿)`）：

| 层 | 作用 | 失效时的行为 |
|---|---|---|
| ① 结构化提示词 | 固定 JSON 结构，要求单行字段值、建议用一两句话概括 | — |
| ② 解析与校验 | `parse_json_block` 容忍围栏/前后废话/**字符串里的真实换行**；Pydantic 校验并规范化（列表转文本、紧急程度纠偏） | 解析或校验失败 → **重试一次**并强调"只输出 JSON" |
| ③ 规则草稿兜底 | 正则抓型号与报错码、关键词判断紧急程度与已尝试操作 | 两次都失败或模型不可用 → 用规则草稿落库，并把失败原因写进工单事件备注 |

实测教训（已固化为测试）：本地 qwen2.5 会把整段回答塞进 `suggestion` 并**带真实换行**，
标准 `json.loads` 会判定为非法 JSON，导致抽取回退、白等 40 秒。
现在解析用 `strict=False` 放宽控制字符，字段值再压成单行，抽取成功率与耗时都恢复正常
（21.9s → 11.3s）。

状态机的合法流转定义在 `app/tickets/service.py` 的 `ALLOWED_TRANSITIONS`，
非法流转一律 400 + 说明。删除会话不会删除工单（工单是留档记录）。

## 7. LLM 接入与降级

| 能力 | 首选 | 备用 | 降级行为 |
|---|---|---|---|
| 对话/抽取 | 本地 Ollama（`qwen2.5:latest`） | DeepSeek API（可关） | 首选失败自动切备用，`mode` 标记并在页面提示 |
| 图片理解 | **本地 Ollama 视觉模型**（`qwen2.5vl:3b`） | 云端网关（`qwen3.5-omni-plus`，可关） | 本地模型未拉取/加载失败 → 自动回退云端，并在结果里标明实际通道 |
| 嵌入 | 本地 BGE-M3 | 无 | 置「仅关键词」模式，检索退化为 FTS5 |
| 离线开发 | `LLM_MODE=mock` | — | 对话与视觉换成确定性假模型，不联网、不需要 Key，用于先跑通后端逻辑 |

统一接口：所有通道都实现 `chat(messages, **kw) -> str`、`chat_stream()`、`available()`、`ping()`，
由 `ChatChain` 串成「首选 → 备用」的降级链，便于注入假客户端做离线测试。

### 7.1 通道实测记录（2026-10-12，RTX 3060 Laptop 6GB）

| 通道 | 模型 | 结果 | 实测延迟 | 结论 |
|---|---|---|---|---|
| 本地 Ollama | `qwen2.5:latest`（7.6B） | ✅ 可用 | 冷启动 72.6s / **预热后 7.2s** | **选为默认**；4.77GB 权重中 3.9GB 入显存，冷启动代价大，服务启动时预热 |
| 本地 Ollama | `qwen3:4b` | ⚠️ 正文为空 | 26.9s | 思考型模型把 token 预算花在推理上；需 `/no_think` 才能用，不设为默认 |
| 备用通道 | `deepseek-chat` | ✅ 连通 | — | 云端通道，Ollama 未启动/无模型时自动接管 |
| 多模态 | `qwen3.5-omni-plus` | ✅ 可用 | — | 网关共 175 个模型；测试图正确读出 `ERROR E05`、`Drum unit not detected`、`Model: L3250` |

回答实测（带 2 条资料片段）正确产出了引用标注：

```
1. 请先检查硒鼓芯片触点是否清洁。根据资料片段 [1]……
2. 如果清洁后问题依旧，请联系售后服务中心进行进一步检查。[2]
```

**工程结论**：① 默认模型用 `qwen2.5:latest`；② 服务启动时后台预热对话模型与嵌入模型，
把冷启动时间从用户请求里挪走；③ 页面用流式输出，首包即可见，弱化整段等待感。

自检命令：`scripts/probe_chat.py`（对话通道 + 延迟）、`scripts/probe_vision.py`（多模态链路）。

### 7.2 模型层作用实测对照（2026-10-12）

同一套后端代码、同一批演示资料、同一个冒烟脚本，只切换 `LLM_MODE`，结果如下：

| 维度 | `LLM_MODE=mock`（离线） | `LLM_MODE=auto`（真实模型） |
|---|---|---|
| 文字回答 | 固定模板 + 首条资料摘要，显式标注「离线模式·未调用大模型」 | 9.7s 出稿、222 个流式增量；按资料分步作答并标注 `[1][2][3][4]`，能结合"刚换过硒鼓"追问保修与更换流程 |
| 图片理解 | 占位描述，置信度 0，明确说明未真正识别 | 8.6s 识别出**型号 L3250、错误码 E05、英文提示 `Drum unit not detected`，置信度 1.0** |
| 图片信息进入后续链路 | 无（无错误码可带入） | 自动补进检索查询，工单草稿型号由空变为 `L3250` |
| 工单定稿 | 来源 `llm`（走假模型），填充 **5/6**，型号为空 | 来源 `llm`，填充 **6/6**，型号 `L3250` |
| 检索命中 | 命中（最高分 0.64~0.69，向量走真实 BGE-M3） | 命中（最高分 0.48~0.64） |
| 兜底链路 | 确定性模板，不经模型 | 完全相同（设计如此，避免模型改写"未收录"表述） |
| 后端冒烟 15 项 | 15/15 通过 | 15/15 通过 |
| 外部依赖 | 无网络、无 Key、不需要 Ollama | Ollama `qwen2.5:latest` + 多模态网关（DeepSeek 备用） |

结论：**后端逻辑与模型层解耦**——离线模式足以验证接口、状态机、落库与导出；
换成真实模型后，多出来的是「理解能力」：语义归纳、图片识别、字段补全与可直接交付客户的成稿质量。
演示建议：先用 mock 模式确认流程，再用 auto 模式展示真实效果。

### 7.3 本地视觉模型接入实测（2026-10-12）

视觉通道支持本地 Ollama 与云端网关两种后端，**`VISION_*` 配置优先，留空回落到旧名 `QWEN_*`**，
本地地址自动视为"不需要 API Key"，并在本地为主通道时按 `VISION_AUTO_CLOUD_FALLBACK` 自动挂上云端回退。

| 实测项 | 结果 |
|---|---|
| 通道链（`/api/health`） | `vision-local`（`qwen2.5vl:3b`，本地 Ollama，无需密钥）→ `vision-cloud-fallback`（`qwen3.5-omni-plus`） |
| 识别质量（本地 3B） | 正确读出「型号 L3250 / 错误码 E05 / 报错位置 屏幕顶部 / 鼓单元未检测到」，置信度 0.9；工单草稿自动补上型号 |
| **纯视觉推理** | **8.5s**（560×260 截图，模型已在显存） |
| 一次完整图片问答 | **34.6s** —— 因为 6GB 显存装不下两个模型，流程里有**两次换页**：文本模型卸载 → 载入视觉模型识别 → 再换回文本模型生成回答 |
| 文字问答（热态 / 冷启动） | 4.9s / 27.6s |
| 显存驻留 | `qwen2.5:latest` 占 3.90GB（权重 4.77GB，余量落 CPU）；`ollama ps` 确认两个模型不会同时常驻 |
| 回退验证 | 故意把本地模型名写错 → 4.7s 内自动切到云端通道并成功识别（`provider=vision-cloud-fallback`） |

**工程取舍建议**（按 6GB 显存）：

| 取向 | 做法 | 代价 |
|---|---|---|

### 12.3 前端约定

1. **防 XSS**：所有来自后端或模型的文本一律通过 `textContent` / DOM 节点写入，禁止 `innerHTML` 拼接；
   回答正文的 Markdown 也只做「`**加粗**`、`- 列表`、换行」三类结构化渲染（`UI.richText`）。
   `test/project.test.js` 有专门断言守着这条约定。
2. **状态与权限**：状态点、紧急徽标、可用流转按钮都由统一的状态表驱动；前端只渲染合法按钮，
   最终合法性仍由后端裁决（非法流转返回 400 并在页面提示）。
3. **`hidden` 属性**：抽屉与遮罩用 `hidden` 控制显隐，因此全局有一条
   `[hidden] { display: none !important }` 兜底（否则会被组件自身的 `display: flex` 覆盖）。
4. **缓存**：静态资源由 `StaticFiles` 提供并带 ETag/Last-Modified，普通刷新即可拿到最新版本。

## 13. 检索增强链路（v2.1）

对应 `docs/需求规格说明书.md` 第 13 节。目标：让"语义不全 / 多实体歧义"的问题被正确识别，
并用精排 + 动态 TopK 把无关片段挡在提示词之外。

### 13.1 新增模块与节点落地

| 模块 | 职责 |
|---|---|
| `app/rag/reranker.py` | 本地 CrossEncoder 封装（懒加载、批量、线程安全、失败降级）；权重缺失时用**词面覆盖率兜底重排** |
| `app/rag/fusion.py` | `Candidate` 统一候选结构（内部片段 / 联网结果）、**N 路 RRF 融合**（来源权重、归一化到 0~1）、**动态 TopK 选择** |
| `app/rag/web_search.py` | MCP 联网检索客户端（百炼 EnhancedSearch `search_pro`）：结果规范化、超时与失败隔离、**可判别实体过滤**、**内容词覆盖率**（联网触发的第二信号） |
| `app/rag/confidence.py` | 三档置信判定（第一段粗判 + 第二段终判）、澄清与拒答话术、实体池、域内/代词识别 |
| `app/rag/rewrite.py` | 查询变体（规则版）、**一次调用产出意图+实体+查询式**的可选 LLM 对齐、结果合并 |

图节点实现（`app/graph/nodes.py`）与需求节点的对应：

| 需求节点 | 实现 | 说明 |
|---|---|---|
| ① 意图确认与改写 | `intent_align` | 实体池（图片/草稿/历史）+ 第一段判定 + 查询变体；边界且 `LLM_ALIGN_ENABLED=true` 时才调一次模型 |
| ② 并发召回 | `recall_internal` + `fuse_rerank` 内 | 内部多查询变体召回；**联网触发依赖内部重排结果**，故在同一节点内判定（内部命中即不联网，可断言） |
| ③ RRF 融合 | `fuse_rerank` | 内部多路 + 联网候选并入后再次融合 |
| ④ 重排 | `fuse_rerank` | 查询 = 原始问题 + 已知实体（实测：缺实体会让最相关片段被打低分） |
| ⑤ 动态 TopK | `fuse_rerank` | `select_supporting`，返回截断原因 |
| ⑥ 生成/兜底/反问/拒答 | `generate_answer` / `fallback_answer` / `clarify` / `reject_low` | 反问与拒答为确定性模板，不经模型 |

> 为什么 ②③④⑤ 放在一个节点里：联网触发要看内部候选的重排结果，拆开就必须把候选在状态里
> 来回搬运，而图状态要被 checkpointer 序列化，候选只能以 dict 传递。合并后逻辑更清晰。

### 13.2 打分与选择规则

```
候选来源：内部（FTS5 + 向量，多查询变体）/ 联网（MCP snippet）
融合：   rrf = Σ_c  weight_c / (60 + rank_c)   → 再归一化到 0~1（理论满分 = 1.0）
精排：   rerank_score = sigmoid(CrossEncoder(query, text))
选择：   score = rerank_score ?? rrf_norm
         floor = max(RERANK_MIN_SCORE, top1 × RERANK_RELATIVE_FLOOR)
         保留 score ≥ floor；自第 2 条起若 score < 上一条 × RERANK_CLIFF_RATIO 立即截断；最多 RERANK_TOP_K_MAX 条
```

选择规则天然覆盖"低置信"：当 `top1 < RERANK_MIN_SCORE` 时 `floor` 高于所有候选，结果集为空 → 由上层走兜底。

### 13.3 并发召回与线程模型

| 通道 | 实现 | 并发方式 |
|---|---|---|
| 内部知识库 | sqlite（FTS5 + sqlite-vec），使用请求自带的连接（`check_same_thread=False`） | `ThreadPoolExecutor(2)` 提交为任务 |
| MCP 联网 | `mcp` SDK 的 Streamable HTTP 客户端（异步） | 同线程池任务内 `asyncio.run()`，**每次调用自建一次会话**（无状态、无共享事件循环问题） |

两路各自设超时并捕获异常：任一路失败只记录原因，另一路结果照常返回（失败隔离）。

### 13.4 降级矩阵

| 失效项 | 行为 |
|---|---|
| reranker 权重缺失 / 加载失败 | 自动使用 `LexicalFallbackReranker`（查询词覆盖率，0~1），`trace.rerank = "fallback"` |
| MCP 未配置 / 禁用 / 超时 / 报错 | 只用内部结果，`trace.web_used=false` 且记录原因 |
| 联网结果不含问题实体 | 丢弃该条（`MCP_REQUIRE_ENTITY_MATCH=true`），避免"网上同名错误码含义不同"污染答案 |
| 内部已高置信 | **不触发联网**（可断言 MCP 未被调用） |
| 最终支撑集为空 | 走兜底话术（资料未收录 + 转人工），与"拒答"话术分开 |

### 13.6 阈值标定实测（2026-10-12，真实 bge-reranker-large）

`scripts/calibrate.py` 在演示语料上跑出的 top1 分布：

| 问题类型 | 问题 | rerank top1 | 动态 TopK 结果 |
|---|---|---|---|
| 可回答 | 硒鼓怎么更换 | **0.999** | 保留 1/3（cliff 截断，0.456 被砍） |
| 可回答 | 打印机显示 E05 是什么意思 | **0.996** | 保留 1/3（floor 截断） |
| 可回答 | 保修期是多久 | **0.613** | 保留 1/1 |
| 可回答 | 无线网络连不上怎么办 | **0.896** | 保留 1/1 |
| 无关 | 预订国际航班机票价格 | **0.000** | 保留 0/4 → 兜底 |
| 无关 | 今天北京天气怎么样 | **0.000** | 保留 0/4 → 兜底 |
| **语义不全** | 保修期是多少？ | 0.355 | 中置信 → 反问 |
| **语义不全** | 坏了怎么办？ | 0.226 | 中置信 → 反问 |
| **语义不全** | 这个多少钱？ | 0.015 | 低置信 → 拒答 |

**结论**：

1. `CONFIDENCE_HIGH=0.50`、`CONFIDENCE_LOW=0.10` 在实测上完全分离——可回答问题 ≥0.613，
   无关问题 =0.000，中间地带只出现在"问得不清楚"的问题上；
2. **重排分能判"资料够不够"，但判不出"问题清不清楚"**：语义不全的问题 top1 分布在 0.015~0.355，
   横跨中/低两档，仍会有 0.355 这种"有点像"的情形。这正是要保留**第一段实体粗判**的实证依据
   ——两段式不是设计冗余，而是各自解决不同问题；
3. 精排把小语料里的无关项直接压到 0.000（原融合分是 0.21），区分度提升一个量级；
4. `RERANK_CLIFF_RATIO=0.5` 偏严：像"硒鼓怎么更换"只留 1 条，把 0.456 的同文档另一章节砍掉。
   当前取"宁少勿滥"（噪声进提示词的代价高于少一条片段），如觉得答案不够全面，
   把 `RERANK_CLIFF_RATIO` 调到 0.3~0.4 即可放宽。

### 13.7 联网过滤实测与"联网可能就是没用"

用真实百炼 MCP 查询「L3250 报错 E05 怎么处理」，返回 5 条结果，逐条检查：

| 检查项 | 实测结果 |
|---|---|
| 含 `E05` 的条数 | **5 / 5** |
| 含 `L3250` 或品牌「云打」的条数 | **0 / 5** |
| 这 5 条讲的是什么 | 清一色 Canon 喷墨机「E05 = 墨盒未识别」，与本公司激光机手册「E05 = 硒鼓未识别」**正好相反** |
| 按**型号**过滤 | 丢弃 5/5 → 联网零贡献（这正是正确结果：网上确实没有本产品的资料） |
| 按**错误码**过滤 | 5/5 全部通过 —— 等于不过滤，**因此已明确禁用**（`is_discriminating_entity` 会把错误码剔除） |
| 只给错误码、不给型号 | 直接跳过，**不发网络请求**（0ms），`error` 里说明"已忽略错误码" |
| 关闭 `MCP_REQUIRE_ENTITY_MATCH` | 取回 5 条（仅作展示，不作答案依据） |

**结论**：联网通道的正确行为**经常是"什么都不用"**。对真实品牌（网上有资料）它有价值；
对内部专用/虚构产品，它会诚实地返回 0 条，而不是把别家的解决方案塞给客户。
如果不过滤，模型完全可能照着 Canon 的页面让客户去换墨盒 —— 这正是要防的幻觉。
所以触发条件（内部证据不足）与实体过滤（只认型号/品牌）缺一不可，
且**没有型号时宁可不要联网结果**。

|---|---|
| 明确问题「我的打印机报错E05，硒鼓刚换过」 | 意图=high、实体=E05、查询 2 条；精排 20 候选→保留 6、top1 **0.9967**、截断=cap；终判 high |
| 中置信（上文两台机器，问「保修期是多少？」） | 走 `clarify`，候选 **L3250/M1136**，无引用、不生成答案 |
| 低置信（全新会话问「保修期是多少？」） | 走 `reject`，话术要求补充型号，无引用 |
| 场外问题「帮我订机票」 | 终判 low、支撑集 0 条 → 兜底话术 |
| 工单 | 来源 llm、填充 6/6 |

**缺陷 1：重排分与"问得不清楚"无关** → 见 13.6 结论 2，最终由"检索前粗判 + 检索后终判"两段式覆盖。

**缺陷 2：型号词会把重排分抬高到 0.74~0.84，导致联网永不触发**。实测：

| 问题 | 内部重排 top1 | 资料里有没有这个主题 |
|---|---|---|
| L3250 的硒鼓能不能回收，有没有环保处理渠道 | **0.743** | 没有（"回收/环保"未收录） |
| L3250 有没有以旧换新活动 | **0.845** | 没有 |

两个问题都会因 `top1 ≥ 0.35` 而**跳过联网**，兜底/吞掉。原因：bge-reranker-large 看到型号词
匹配就给高分，它衡量的是"主题相关性"，不是"资料是否回答了这个问题"。

**修法**：引入正交信号 —— **问题内容词覆盖率**（`question_coverage`，剔除虚词与实体词，
看实词是否出现在候选里）。联网触发条件改为二选一：

```
top1 < MCP_TRIGGER_TOP1(0.35)  或  coverage < MCP_TRIGGER_COVERAGE(0.34) → 联网
```

实测效果：「以旧换新」覆盖率 ≈0（型号匹配但主题没收录）→ 联网触发；
「E05 怎么处理」覆盖率 ≈1（报错处理在资料里）→ 不联网。
两个信号互补：**覆盖率管"资料里有没有这个主题"，重排分管"资料够不够对口"**。

同时保底：即使两个信号都没触发，生成阶段的反幻觉提示词也会让模型如实回答
"内部资料中未收录该信息"，不会编造 —— 这是多层防护，不依赖单一开关。

## 14. 转人工闭环与界面权限边界（V3）

### 14.1 界面权限边界

| 页面 | 谁能看 | 入口 |
|---|---|---|
| `/`（客户对话） | 客户 | 只有对话本身；**没有**工单台、没有接口文档入口 |
| `/admin`（工单台） | 人工客服 | 直接访问（不加口令，内网/演示环境） |
| `/selftest`（自检页） | 开发 | 直接访问 |
| `/docs`（FastAPI 文档） | 开发 | 直接访问，不在任何页面暴露 |

### 14.2 转人工时序

```
客户：「我要转人工」/ 点「🙋 转人工客服」
   │
   ├─ chat.py：话术识别命中（或 handoff 接口被调用）
   │    → HandoffService.request()
   │        · conversations.handoff_state = requested（+ 原因、时间）
   │        · 系统提示写入消息（role=system，客户页显示为居中提示条）
   │        · **立即建单**：紧急度至少「较急」+ 时间线记「客户请求转人工」
   │          （工单原本次「结束会话」才建，但那时客服台没有可提醒的载体；
   │            建单只用工单草稿，不调模型——客户在等，不能为建单再等 10s）
   │    → 本轮不再调用模型，只回一句等待提示
   │
   ├─ 工单台 /admin：顶部「🔔 转人工提醒」每 5 秒刷新
   │    · 计数：等待接入 / 人工中；标题前缀 + 脉冲高亮提醒客服
   │    · 每条显示工单号、最后一句消息、已等待时长
   │
   ├─ 客服点提醒（或工单详情里的「💬 打开客户会话」）
   │    → 右下会话面板：历史消息 + 输入框；每 3 秒增量拉取客户新消息
   │    → 首次发言自动把状态置为 claimed（人工中）
   │
   ├─ 客户页：每 3 秒轮询 GET /messages?after_id=
   │    → 客服发言以「客服」气泡追加；刷新页面后仍会继续轮询
   │
   └─ 人工期间客户再提问 → AI 静默（只入库 + 提示等待），避免机器人抢答
```

### 14.3 数据结构与接口

| 项 | 说明 |
|---|---|
| `conversations.handoff_state` | `none` / `requested` / `claimed`；`handoff_reason`、`handoff_at` |
| `messages.role` | 新增 `agent`（客服发言）与 `system`（系统提示） |
| 迁移 | `SCHEMA_VERSION 1→2`，`db.migrate()` 幂等补列 + 补索引；**索引必须放在补列之后**（老库先建索引会报 no such column，真机踩过） |
| 接口 | `POST /api/conversations/{id}/handoff`、`GET /api/handoffs`、`POST /api/conversations/{id}/agent-messages`、`GET /api/conversations/{id}/messages?after_id=` |

### 14.4 实测（真实模型，冒烟 22/22）

| 场景 | 结果 |
|---|---|
| 客户说「我要转人工」 | handoff 事件 + 工单 `T-…-0012` 立即生成，本轮不回答 |
| 工单台提醒 | `waiting=1`，含工单号与等待时长 |
| 人工期间客户追问 | 继续静默，状态保持 requested |
| 客服回复 | 状态转 claimed，客户增量轮询拿到 1 条 `role=agent` |
| 结束会话 | 复用同一张工单，紧急度「较急」 |

### 14.5 结束人工服务（V4）

客服在会话面板点「✅ 结束会话」→ `POST /api/conversations/{id}/handoff/finish`：

```
① 把人工阶段的对话重新抽取进工单字段（真实模型，实测 2.7s；失败自动退化为规则抽取，
   整体异常也只记一条时间线，不阻断结束）
② 工单置「已解决」——按状态机合法路径：待处理 →（处理中）→ 已解决；
   已是已解决/已关闭则不擅自重开，只留痕
③ handoff_state = done + 会话 status = closed → **立即从「转人工提醒」栏移除**
④ 写一条系统提示给客户（客户页轮询可见）：「本次人工服务已结束…机器人会重新为你服务」
⑤ 工单时间线留痕，三处信息一致
```

另外补了一个**容易漏掉的清理**：客户在等待人工时自己点了「结束会话并生成工单」，
原先只建单、不清提醒，那条会话会**永远挂在提醒栏**（实测残留 3 条）。现在
`close` 会调用 `HandoffService.clear_active()` 顺手清掉提醒并留痕，工单状态不受影响。

接口：`POST /api/conversations/{id}/handoff/finish`、`GET /api/handoffs/history`（最近已完成，供回看；
提醒栏不展示，符合"彻底移除"的取舍）。

实测（真实模型）：转人工 → 客服接入 → 客户补充「L3250 E05」→ 结束会话 **2.7s**，
字段同步来源 `llm`、更新 `error_info/product_model/urgency`，工单 `T-20261013-0002` 置「已解决」，
提醒栏 `waiting/serving` 归零，客户侧最后一条为 system 提示。
